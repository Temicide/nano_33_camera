Comparative Evaluation of Microcontroller-Bound Object Detection Models for the Arduino Nano 33 BLE: Architectural Optimization, Memory Budgets, and SRAM CharacterizationCharacterization of SRAM in Microcontroller-Bound Deep LearningDeploying deep learning-based computer vision models to resource-constrained microcontrollers requires a rigorous understanding of the underlying physical memory hierarchy. Static Random-Access Memory (SRAM) is a type of volatile semiconductor memory that uses bistable latching circuitry, typically composed of six-transistor (6T) cells, to store each bit of data. Unlike Dynamic Random-Access Memory (DRAM), which stores data in a single transistor and capacitor pair, SRAM does not require periodic electrical refreshing to maintain its state. This latching mechanism allows SRAM to provide exceptionally low-latency access—frequently executing in a single CPU clock cycle—and to operate with minimal dynamic power consumption. Because of these characteristics, SRAM is integrated directly onto the same silicon die as the microcontroller unit (MCU) core.However, the physical footprint of a six-transistor cell is substantially larger than a DRAM cell, which significantly limits the amount of SRAM that can be economically placed on an MCU die. Consequently, typical microcontroller architectures are bound to small on-chip SRAM allocations, generally ranging from $32\text{ KB}$ to $512\text{ KB}$.In contrast, Flash memory is a non-volatile, block-addressable storage medium used to retain read-only program code and quantized neural network weights. Because accessing Flash memory is slower than accessing SRAM—often introducing two to three CPU wait states on Cortex-M microcontrollers—critical parameters and volatile variables must be executed within the SRAM boundary. Thus, SRAM acts as the primary working memory where the active program stack, the heap, the camera peripheral buffers, and the intermediate neural network activation tensors must reside.The Arduino Nano 33 BLE is built upon the Nordic Semiconductor nRF52840 system-on-chip, which features a $32\text{-bit}$ ARM Cortex-M4F processor running at $64\text{ MHz}$, supported by $1\text{ MB}$ of CPU Flash and $256\text{ KB}$ of SRAM. Under the ARM Mbed operating system (OS) used by the board, a significant baseline portion of this $256\text{ KB}$ SRAM is consumed by the OS scheduler, peripheral drivers, and Bluetooth Low Energy stack.This creates a critical memory constraint for developers. Compile-time memory statistics generated by standard integrated development environments are highly deceptive because they only account for global static allocations. At runtime, the system must support three distinct memory consumers according to the True Dynamic RAM Equation :$$RAM_{\text{dynamic}} = RAM_{\text{static}} + SRAM_{\text{buffer}} + SRAM_{\text{arena}}$$In this equation, $RAM_{\text{static}}$ is the baseline static variable footprint, $SRAM_{\text{buffer}}$ is the raw camera image frame buffer, and $SRAM_{\text{arena}}$ is the TensorFlow Lite Micro tensor arena. For a Quarter-QVGA (QQVGA) camera stream captured at $160 \times 120$ pixels in RGB565 format ($2\text{ bytes}$ per pixel), $SRAM_{\text{buffer}}$ demands $38.4\text{ KB}$ of contiguous RAM. If the combined memory allocation exceeds $256\text{ KB}$, or if the remaining heap is too small to accommodate the camera stream, the microcontroller will experience dynamic allocation failures, throwing runtime errors such as "failed to allocate tensor area" or "failed to create buf*mem". Generally, any vision model requiring more than $180\text{ KB}$ of peak RAM during training will fail to run on-device due to these system-level overheads.Comparative Analysis of Lightweight Object Detection ParadigmsTraditional deep learning vision models, such as MobileNet SSD (Single Shot MultiBox Detector), cannot execute within the $256\text{ KB}$ SRAM budget of the nRF52840. These models require the retention of multi-scale feature maps and coordinates for hundreds of bounding boxes, demanding megabytes of RAM. Standard MobileNetV2 classification backbones can also suffer from an imbalanced activation memory distribution where early layers demand massive peak SRAM, even when quantized. To overcome these limits, three lightweight paradigms have emerged: Edge Impulse FOMO (Faster Objects, More Objects), MCUNetV2, and TinyissimoYOLO.FOMO simplifies object detection by framing it as a parallel classification task over a structured spatial grid. Instead of predicting bounding-box scales, it trains specifically on the centroids (center points) of objects, assuming a fixed, square bounding box. It leverages a truncated MobileNetV2 backbone, cutting the network at block_6_expand_relu. For an input image of $96 \times 96$ pixels, FOMO produces a $12 \times 12$ regional probability map, where each cell acts as an independent classifier.The performance of FOMO is heavily influenced by the width multiplier (alpha) of the MobileNetV2 backbone.MobileNetV2 0.35 Alpha: Provides the highest accuracy but requires approximately $240\text{ KB}$ to $245\text{ KB}$ of SRAM. This footprint exceeds the safe limits of the Arduino Nano 33 BLE once Mbed OS and frame buffers are accounted for.MobileNetV2 0.1 Alpha: The optimal choice for the nRF52840, requiring under $100\text{ KB}$ of SRAM and $300\text{ KB}$ of Flash. On an ARM Cortex-M4F running at $80\text{ MHz}$, it achieves approximately $10\text{ fps}$. On the $64\text{ MHz}$ Arduino Nano 33 BLE, it runs at a highly responsive $8\text{ fps}$.MobileNetV2 0.05 Alpha: Reduces memory requirements further, though standard integer quantization pipelines may experience negligible RAM differences compared to the $0.1$ alpha model.MCUNetV2 is designed around a system-algorithm co-design framework. It addresses the imbalanced activation memory distribution of early CNN blocks (where the first five blocks of MobileNetV2 consume up to $450\text{ KB}$ of SRAM) by utilizing a patch-by-patch execution schedule. It operates on small spatial patches of the feature map sequentially, reducing peak SRAM by $4\times$ to $8\times$. While MCUNetV2 achieves a remarkable $64.6\%$ mAP on the Pascal VOC dataset within a $256\text{ KB}$ SRAM budget, the computational complexity of its $67.3\text{ Million}$ MAC operations results in an on-device latency of $3535\text{ ms}$ on a Cortex-M4 CPU, making it impractical for real-time tracking.TinyissimoYOLO is a highly optimized, quantized TinyML object detection network with a total memory footprint under $1\text{ MB}$. On microcontrollers with hardware ML acceleration, it can achieve an on-device latency of only $17\text{ ms}$. When combined with adaptive tiling, TinyissimoYOLO boosts the F1-score of small objects by $225\%$ and reduces the average object count error by up to $89\%$. The resizing options selected in the training studio (such as squash, fit shortest, or fit longest) apply solely to the dataset preprocessing pipeline in the cloud. When running live inference on-device, the deployed C++ library expects the input feature array to match the model's exact input dimensions. If the camera captures a QQVGA ($160 \times 120$) image and the model is trained on $96 \times 96$ inputs, passing the unresized buffer directly to the run_classifier() function will fail.Developers must manually crop and scale the raw image buffer prior to execution. While allocating a secondary $96 \times 96$ buffer in SRAM to store the scaled image is a common approach, it wastes precious memory. A more efficient method is to perform in-place bilinear downsampling directly within the camera buffer, or invoke the undocumented Edge Impulse SDK helper function resize_image(), which optimizes spatial downscaling.Color format conversion represents another critical memory and processing bottleneck. Microcontroller camera modules, such as the OV7670, output raw pixel data in RGB565 format. In this format, each pixel is represented by a $16\text{-bit}$ integer ($2\text{ bytes}$), with 5 bits allocated to red, 6 bits to green, and 5 bits to blue. To convert these pixels to the standard $24\text{-bit}$ RGB888 format ($3\text{ bytes}$ per pixel) expected by typical deep learning models, developers must execute a series of bit-shifting and binary masking operations for each pixel, $p$ :$$R*{888} = ((p \gg 11) \ \& \ 0\text{x}1\text{F}) \ll 3$$$$G*{888} = ((p \gg 5) \ \& \ 0\text{x}3\text{F}) \ll 2$$$$B*{888} = (p \ \& \ 0\text{x}1\text{F}) \ll 3$$While RGB888 maintains high color fidelity, converting a $96 \times 96$ image to RGB888 increases the input layer size to $27,648\text{ features}$, significantly inflating the subsequent tensor arena. Converting the camera feed directly to a grayscale monochrome format ($1\text{ byte}$ per pixel) is the single most effective optimization. Grayscale conversion reduces the input layer of a $96 \times 96$ image to exactly $9,216\text{ features}$, saving approximately $18.4\text{ KB}$ of input buffer memory and reducing the peak working set of the first convolutional layer.Another severe source of memory waste is the allocation of duplicate image buffers within the camera driver code. Standard camera libraries read raw data into a byte array before copying it into an integer array for processing, which duplicates the $38.4\text{ KB}$ buffer. Optimization and Execution FrameworksThe runtime efficiency of deep learning models on resource-constrained microcontrollers is governed by the underlying inference library and compiler optimization strategies.TFLM avoids dynamic heap allocation (such as standard malloc or free calls) during inference to eliminate runtime heap fragmentation. Instead, all mutable tensors (activations, temporaries, and scratch buffers) are statically packed into a contiguous segment of SRAM known as the tensor arena. The minimum size of the tensor arena, $A$, is mathematically determined by analyzing the lifetime overlap of all network tensors :$$A \geq P + \max*{t} \sum*{i: t \in \ell_i} s_i$$where $P$ is the persistent buffer size, $s_i$ is the size of a temporary tensor $i$, and $\ell_i$ is its active lifetime interval $[t_i^{\text{start}}, t_i^{\text{end}}]$. TFLM implements a first-fit decreasing bin-packing algorithm via the GreedyMemoryPlanner to optimize the reuse of these overlapping memory windows. However, for standard convolutional neural networks, the peak working set is highly dependent on the architecture; if intermediate feature maps must be preserved across multiple parallel branches, the arena size will swell.To bypass the memory overhead of the TFLM interpreter, Edge Impulse provides the EON Compiler. While standard TFLM requires a runtime interpreter to parse flatbuffer network graphs, EON compiles the neural network directly into optimized, static C++ source code. This compiler-generator approach eliminates the flatbuffer parsing code, saving $25\text{--}55\%$ of SRAM and up to $35\%$ of Flash memory compared to the standard TFLM runtime interpreter, while maintaining identical model accuracy.To achieve low latency on Cortex-M4 and Cortex-M7 architectures, compilers leverage ARM's official open-source CMSIS-NN library. CMSIS-NN provides highly optimized low-level kernels for key neural network layers, such as convolutions, depthwise separable convolutions, pooling, and activations. It utilizes the Cortex-M4F processor's DSP instruction set extensions, enabling Single Instruction Multiple Data (SIMD) operations to perform multiple parallel $8\text{-bit}$ integer multiply-accumulate (MAC) calculations in a single instruction cycle. On Cortex-M4 platforms, CMSIS-NN delivers a $2.4\times$ improvement in inference throughput and a corresponding $4.9\times$ reduction in energy consumption compared to reference C implementations.Neural networks trained in floating-point precision ($32\text{-bit}$ floats) must be quantized to $8\text{-bit}$ integers (INT8) prior to deployment. Post-training quantization achieves a $3\times$ to $4\times$ reduction in Flash storage size and reduces the required tensor arena SRAM footprint by approximately $4\times$, with a negligible accuracy degradation of only $0.3\%\text{ to }1.2\%$. The Arduino Nano 33 BLE lacks the physical memory required to run unquantized (float32) models, making 8-bit quantization mandatory for deployment.Engineering Synthesis and Deployment RecommendationsFor developers seeking the best object detection model for the Arduino Nano 33 BLE that uses the least RAM while maintaining the best real-time performance, the definitive choice is Edge Impulse FOMO with a MobileNetV2 0.1 Alpha backbone, configured for $96 \times 96$ (or $64 \times 64$) grayscale inputs and compiled using EON with 8-bit quantization.MCUNetV2 is technically superior for high-resolution bounding box localization, but its $3.5\text{-second}$ latency on Cortex-M4 hardware makes it impractical for real-time applications. TinyissimoYOLO offers exceptional speed but requires external hardware accelerators or specialized neural processing units (NPUs) that are absent on the nRF52840. FOMO running on the EON compiler with CMSIS-NN acceleration achieves a highly responsive frame rate of approximately $8\text{ fps}$ on the Arduino Nano 33 BLE.
