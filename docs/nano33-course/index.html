What this little counter actually does

Imagine a document scanner at a pharmacy counter: a camera sees the blister pack, a tiny model finds each pill cell, and the board reports the count over USB.

Start from the thing you can see

The project turns an Arduino Nano 33 BLE and OV7675 camera into a small medicine blister counter. The key trick is that the firmware runs the camera capture and the inference on the board itself.

1

Camera frame

The OV7675 produces a 160x120 grayscale picture, small enough for microcontroller RAM.

2

Model input

The frame is center-cropped and downsampled to the Edge Impulse model size: 96x96.

3

Serial result

USB serial sends raw frames, detection packets, or JSON count results to the laptop.

The main journey: send J, get a count

Think of the command as a ticket number at a service desk. The laptop sends one letter, and the board runs a complete capture-count-report cycle.

How pixels travel over serial

The board and laptop use a tiny shipping label: magic bytes say what kind of package is coming, then the payload follows.

Two packet types, two jobs

Serial is not automatically structured. The project creates structure by prefixing each binary packet with a short magic byte marker.

OVF1 Raw frame packet: header plus grayscale image bytes.
OVD1 Detection packet: header, bounding boxes, then the same grayscale image bytes.
JSON Single-shot count response for production checks and scripts.

When bytes cross a boundary, both sides need the same contract. In this project, the C++ writer and Python reader must agree on byte order, field order, and packet size.

The Python reader follows the contract

def read_packet(ser):

04

How the model sees a smaller world

The camera sees a postcard-sized frame. The model wants a square passport photo. The firmware builds a precise crop-and-resize map between them.

Why preprocessing matters

Preprocessing is the promise that training and production see the same kind of image. Here, the camera captures 160x120 grayscale pixels, but the Edge Impulse FOMO model expects a 96x96 grayscale input.

160

Camera frame

Large enough to see the blister pack, small enough to fit in RAM.

96

Model input

The trained model only understands the input shape it was exported with.

int8

Tiny data type

The model uses compact values to keep memory use practical on the Nano 33 BLE.

The firmware refuses incompatible model exports

A compile-time check is like a measuring gate at the workshop door. If the model shape no longer matches the firmware assumptions, the build stops before upload.

CODE 
static_assert(kInferPixels == EI_CLASSIFIER_DSP_INPUT_FRAME_SIZE,
              "Edge Impulse DSP input must match a single grayscale frame");
static_assert(kFrameWidth >= kInferWidth && kFrameHeight >= kInferHeight,
              "Camera frame must be at least as large as model input");
PLAIN ENGLISH

Confirm the model input pixel count matches one grayscale frame.

If not, stop compilation with a message that explains the mismatch.

Confirm the camera frame is at least as wide and tall as the model input.

If the model is larger than the camera frame, stop before producing bad firmware.

The upload script protects RAM

RAM is one of the tightest constraints in this repository. The upload script parses Arduino compile output and blocks unsafe builds.

CODE 
if (( DYNAMIC_BYTES > RAM_MAX_BYTES )); then
  echo "ERROR: dynamic memory ${DYNAMIC_BYTES} exceeds hard limit ${RAM_MAX_BYTES}." >&2
  echo "Re-export the Edge Impulse model with a smaller arena before uploading." >&2
  exit 1
fi
PLAIN ENGLISH

If the compiled firmware uses more dynamic memory than the hard limit...

print an error that includes the measured bytes and the allowed maximum.

tell the human the likely fix: export a smaller Edge Impulse arena.

stop the script so unsafe firmware is not uploaded.

!
Common AI Mistake

If an AI assistant suggests removing memory limits to make upload pass, push back. The limit is protecting hardware behavior, not merely making the script strict.

Spot a real command mismatch

This is the kind of bug that appears when two files disagree about the protocol. The firmware uses lowercase c for calibrated exposure, while uppercase C runs a single count.

Which line makes calibrated mode send the wrong firmware command?

1 mode_cmd = {"auto": b"A", "face": b"F", "calibrated": b"C", "stream": b"S"}
2 if args.mode in mode_cmd:
3 ser.write(mode_cmd[args.mode])
4 print(f"Sent mode command: {args.mode}")

The root cause is the dictionary value for calibrated mode. This is a protocol mismatch: one side says C means count, the other side tries to use C for calibration.
